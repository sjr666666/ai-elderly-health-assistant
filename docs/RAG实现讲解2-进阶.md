## 一、架构重构：RagSearchService（为什么必须抽这一层）

### 问题：构造器循环依赖

第一阶段的 RagService 依赖 `DeepSeekService`（生成要用 LLM）。如果第二阶段要让
"药品补全/冲突检测/今日一课"这些**已有功能**也使用检索能力，它们都在 `DeepSeekServiceImpl` 里实现——
`DeepSeekServiceImpl` 就得依赖 `RagService`，于是：

```
RagService ──依赖──▶ DeepSeekService
     ▲                    │
     └──────── 循环依赖 ──┘
```

Spring **构造器注入**遇到循环依赖会直接启动失败（报 BeanCurrentlyInCreationException）。

### 解法：抽出"纯检索层"，依赖倒置

```
            ┌─────────────────────────────┐
            │  RagSearchService（纯检索）  │  ← 只做 向量/关键词 检索，不依赖 LLM
            └────────────┬────────────────┘
                         │ 被两边同时依赖
        ┌────────────────┴────────────────┐
        ▼                                 ▼
  RagService（编排）                DeepSeekServiceImpl（存量功能增强）
  依赖: RagSearchService             依赖: RagSearchService
       + DeepSeekService
```

- `RagSearchService`：`search(query, topK)` 返回 `{mode, hits}`；`formatContext(query, topK)` 直接返回拼好的 `[1][2] 参考资料` 文本
- `RagService` 和 `DeepSeekServiceImpl` **都只依赖 RagSearchService**，循环消失
- 附带收益：**检索成为独立可复用能力**——任何功能想要"知识依据"，注入 RagSearchService 即可

**面试讲法**："存量系统引入 RAG 时，先抽一个不依赖 LLM 的纯检索层，避免 RAG 编排服务与 LLM 实现互相注入形成循环依赖；同时把检索沉淀成公共能力，多个 AI 功能共用。"

## 二、P4：接入现有 AI 功能（RAG 增强存量功能）

改造了三处，都在 `DeepSeekServiceImpl`，核心手法一致：**调用 LLM 前先用 RagSearchService 检索，把资料注入 prompt，让模型"照着资料答"**。

### 1. 药品信息补全（queryDrugInfoWithAI）

**改造前**：`"请根据你的医药知识尽力填写"` → 纯靠模型记忆，会编。
**改造后**：

```
1. ragSearchService.formatContext(drugName, 3)  // 从知识库检索该药
2. userPrompt = 参考资料 + "请优先根据上述参考资料填写成分、适应症..."
3. systemPrompt 增加规则："优先使用参考资料中的信息"
```

效果：OCR 识别出药名后，补全的字段来自知识库（drug_base 说明书原文），模型只在资料缺失时才补充记忆。

### 2. 冲突检测（analyzeDrugConflicts）

**改造后**：`context = formatContext(药品列表拼接, 3)` → 注入到 userPrompt 开头。
效果：AI 判断"阿司匹林 × 降压药"冲突时，能看到知识库里的药效/成分资料，而非只凭训练记忆。

### 3. 今日一课（generateDiseaseScienceLesson）

**改造后**：`context = formatContext(diseaseName, 3)` → 注入 userPrompt，
附言"请优先参考上述参考资料中的管理要点，用你自己的话通俗表达"。
效果：科普内容与知识库指南一致（如高血压指南里的限盐、自测血压建议），不再纯靠模型发挥。

**面试讲法**："RAG 接入存量 AI 功能不用重写，在 prompt 组装处加一次检索注入即可——这是 RAG 对现有系统最轻的侵入方式。三处改造共用同一个 RagSearchService.formatContext，零重复代码。"

## 三、P3：前端「用药问问」问答页

### 组件设计（RagAskCard.jsx）

- 复用老人端 `daily-lesson-card` 视觉体系（同一卡片风格，视觉一致）
- 输入框 + 提问按钮（回车触发），调 `POST /api/rag/ask`
- 展示三块：**药箱提示**（💊 根据您的药箱：XXX）、**回答正文**（pre-wrap 保留换行）、**引用来源**（[1] 标题 + 来源标注）
- 模式徽标：智能检索 / 关键词检索 / 本地知识（对应后端 mode）

### 为什么能"零鉴权代码"

前端用 `elderFetch`（`utils/elderApi.js`）——它自动带 `elderToken`，401 自动刷新并重新请求。所以 RAG 接口的 JWT 认证、token 刷新全是**复用既有能力**，组件里一行鉴权代码都不用写。

**面试讲法**："前端复用统一的 elderFetch 封装，JWT 头、token 自动刷新、过期跳登录都是横切能力，业务组件只关心数据展示——这是前端对后端认证体系的最小依赖。"

## 四、P2：检索单测（为什么测、怎么测）

三个测试类共 14 个用例，覆盖：

| 测试类 | 验证点 |
|---|---|
| `KeywordIndexTest` | bigram 倒排命中正确性、多关键词排序、Top-K 限制、无匹配返回空 |
| `VectorStoreTest` | 归一化向量点积排序（相似方向排第一）、Top-K、分数单调递减 |
| `RagIngestServiceTest` | Markdown front-matter 解析（title/source/tags/正文）、无 front-matter 回退标题行、资源文件数量约定（10 指南 + 12 FAQ）、每个文件可解析 |

**测试驱动发现的两个真实问题**（这比测试本身更有价值）：

1. **bigram 误撞**：`"维生素B12"` 的 bigram `"生素"` 撞上"抗生素"切片 → 暴露了 bigram 检索的固有局限（词项过短易误匹配）。测试用完全无重叠的查询验证"无匹配返回空"。
2. **无 front-matter 时正文残留标题行** → 改为提取标题后从正文移除 `# 标题` 行，正文更干净。

**面试讲法**："单测不是走过场——检索类代码的正确性直接决定回答质量，而且写测试时能暴露实现边界（如 bigram 误撞）。RAG 的检索层是最适合单元测试的部分，因为它不依赖外部服务。"

## 五、面试补充 Q&A

**Q1：存量 AI 功能接入 RAG，最优雅的改法？**
抽纯检索层（RagSearchService），在 prompt 组装处注入 `formatContext` 的结果，零重复代码、零循环依赖。不需要改数据流，只是"给 LLM 喂了参考资料"。

**Q2：检索层为什么独立成服务？**
单一职责 + 解循环依赖 + 可复用。检索（RagSearchService）与编排（RagService）分离后，任何功能都能独立使用检索能力，也方便将来替换检索实现（如向量库换 Milvus）。

**Q3：前端接入 RAG 接口要做哪些安全处理？**
复用统一 API 封装（elderFetch）：JWT 头自动添加、401 自动刷新重试、过期跳登录。业务组件零鉴权代码。

**Q4：怎么证明 RAG 真的"管用"了？**
三层验证：① 单测验证检索命中正确性（P2）；② 接口实测：同一问题对比"接入前后"的回答是否带引用/命中知识库；③ 演示场景：问"我药箱里的药一起吃安全吗"，回答点名用户真实药品（userDrugs 注入）。

## 六、知识库规模化采集 + 检索质量兜底

### 1. 开源数据集采集（脚本化、可复现）

**动机**：116 条知识太少，但人工整理慢。方案：找开源数据集 + 脚本转格式，一次拿到 817 种药。

**选型**：CN-Drug-KG-800（HuggingFace，cc-by-nc-4.0，中文，约 800 药品实体 + 成分/适应症/禁忌/相互作用关系，README 明确标注适合 RAG）。

**实现**（`backend/scripts/rag-dataset/collect_drug_kg.py`）：
```
下载 entities.jsonl + relations.jsonl（实为 JSON 数组）
  → 提取 type=drug 的实体（817 个）
  → 按药品聚合 relations，按 target 类型归类为 成分/适应症/给药途径/禁忌/相互作用/注意事项
  → 子串去重（relations 文本有冗余表达，如"X的功能和适应症是Y；X的功能和适应症"）
  → 生成 knowledge/drugs/*.md（front-matter: title/source/tags）
```
RagIngestService 只加了一行扫描 `knowledge/drugs`，检索侧零改动。

**面试讲法**："知识库规模化靠脚本化采集——数据是开源的（标注来源+许可），采集脚本入库代码仓可复现，原始数据文件不入库（26MB）。加数据不是写代码，是跑脚本。"

### 2. 相似度阈值降级（采集后必做的质量兜底）

**真实踩坑**：知识量从 119 → 936 条后，**降级向量（bigram 哈希）彻底漂移**——问"布洛芬缓释胶囊有什么注意事项"命中了三个中药胶囊（因为 900 多条长文本里"注意事项/胶囊"这些通用 bigram 碰撞严重，把精确药名的特征淹没了）。

**根因**：向量检索"永远有结果"（score 只是高低），原降级条件"无结果才降级"永远不触发。

**修复**（`RagSearchService.search`）：
```java
// 降级条件从「无结果」升级为「无结果 OR top-1 相似度低于阈值」
boolean lowConfidence = hits.isEmpty() || hits.get(0).score < vectorScoreThreshold; // 默认 0.45
if (lowConfidence) { hits = keywordIndex.search(query, topK); mode = KEYWORD; }
```
实测分数：漂移项 top-1≈0.41，相关项≈0.51 → 0.45 阈值有效分隔；配了 bge-m3 后语义相似度通常 >0.5，不会误触发。

**面试讲法**："降级不能只看'有没有结果'，要看'结果可不可信'——向量检索永远有结果，用 top-1 相似度阈值判断置信度，低就交给关键词检索（精确名词是它的强项）。这是知识库扩容后必须做的质量兜底，也是'多级降级'思想的深化：向量不行换关键词，关键词不行还有本地直出。"

### 3. 数据集选型的教训（诚实分享）

CN-Drug-KG-800 以**中药/中成药**为主（817 条里常见西药少，如硝苯地平/布洛芬不在其中）。发现方式：采集后用 `grep` 抽查常见药覆盖——**采集完必须做覆盖度验证**。西药知识由 drug_base 动态抽取补齐（94 种常见药），两条知识源互补。这也说明：任何数据集都有覆盖盲区，多源互补 + 验证是标配。

### 4. 检索质量再兜底：低分尾项过滤 + 标题加权（演示级体验的关键）

知识库扩到 936 条后，实测暴露了「降级向量 + 关键词」两个新问题，都是**参考资料出现无关药**：

| 问题 | 现象 | 根因 |
|---|---|---|
| 向量路径混入无关药 | 问"药过期了还能吃吗"，参考资料出现**右旋糖酐70、田七痛经胶囊**（0.19~0.20 分） | 只要求 top-1 过阈值（0.45），第 2、3 名低分尾项照样返回 |
| 关键词路径混入无关药 | 问"布洛芬缓释胶囊有什么注意事项"，出现**长春胺、秦川通痹胶囊** | bigram 打分对标题/内容一视同仁，内容里"注意事项/有效期"等通用词照样得分 |

**修复 1：相对分数过滤（两路统一）**
```java
// 向量模式：只保留 top-1 的 70% 以上（下限阈值×0.8），宁缺毋滥
hits = filterLowScores(hits, 0.7, vectorScoreThreshold * 0.8);
// 关键词模式：只保留 top-1 的 60% 以上（下限 2）
hits = filterLowScores(hits, 0.6, 2.0);
```
核心思想：**top-1 过阈值只说明"有结果"，第 2、3 名必须与 top-1 相近才算"相关"**——分数断层（0.46 vs 0.20）正是噪声信号。

**修复 2：标题加权（KeywordIndex）**
重建索引时额外记录每条的标题 bigram；打分时**标题命中的 bigram 权重 ×3**，内容命中 ×1。效果：query"布洛芬缓释胶囊…"时，布洛芬标题命中 6 个 bigram = 18 分，长春胺靠内容通用词只有 6 分——**药名在标题的切片天然领先**，与修复 1 的尾切配合后直接过滤。

**实测效果**（四个场景全部干净）：
- 药过期了还能吃吗 → 只剩 FAQ ✅
- 布洛芬注意事项 → 只剩布洛芬缓释胶囊（18 分）✅
- 阿司匹林×降压药 → 只剩 FAQ ✅
- 两药同吃 → 用户药箱的布洛芬 + 阿莫西林（多高分项保留）✅

**面试讲法**："检索质量是 RAG 的地基，光有降级还不够——我做了两层兜底：①**相对分数过滤**：top-1 之外的尾项必须与 top-1 相近才返回，分数断层就是噪声；②**标题加权**：倒排索引里标题命中权重高于内容命中，让精确药名天然领先。这两条保证'参考资料里不出现明显无关的药'，也是回答可信度的最后一道闸。"

### 5. 引用体系：让 [1][2] 从"乱码"变成"可点击溯源"

AI 回答里的 `[1][2]` 编号标注是 RAG 可溯源的载体，但老人根本看不懂。前端做三件事让它活起来：

1. **引用上标**：回答里的 `[1]` 正则替换成绿色胶囊上标（`<sup class="rag-cite">`），**点击后平滑滚动到对应资料卡片并闪烁高亮**（`scrollIntoView` + CSS 动画 + 事件委托）
2. **引用感知展示**：解析回答文本中的 `[n]` 集合，下方参考资料**被引用的标"✓ 已引用"（正常显示），没被引用的降透明度标"未采用"**——让用户理解"不是系统乱给资料，而是 AI 没用它"
3. **LOCAL 降级兼容**：无 LLM 时回答是资料原文（无编号），此时不显示"未采用"标签，全部正常展示

**面试讲法**："引用编号不是装饰——前端把它做成**双向锚点**：回答里的 [1] 可点击跳到来源，来源列表标注'已引用/未采用'。这既解决老人'这数字是啥'的困惑，也是 RAG 可溯源承诺的完整闭环：**答案的每一句话都能指到它的出处。**"
