# RAG 用药知识库实现讲解（面试向）

> 本文面向两件事：一是把「AI药管家」RAG 功能的实现讲透，二是整理成你面试时能直接讲的表达。
> 配套代码：`backend/src/main/java/com/example/backend/service/rag/` 包 + `V5__create_knowledge_chunk.sql`

---

## 一、先用一句话说清楚 RAG 是什么

> **RAG = Retrieval-Augmented Generation（检索增强生成）**：大模型回答问题前，先从知识库里"查资料"，再把查到的资料塞进 prompt，让它"照着资料答"。

它解决的核心问题是 **幻觉（Hallucination）**——大模型训练完就"定型"了，不知道你的私有数据，答错了还会一本正经地编。RAG 让模型每次回答前都有"参考资料"，回答可溯源、可更新（知识库改了就生效，不用重新训练模型）。

**为什么医疗场景必须有 RAG**：用药建议错了可能出人命。让模型凭记忆回答"阿司匹林和降压药能一起吃吗"，它可能编；让它先检索到说明书/指南再回答，答案有出处，错了能找到责任链。这就是本项目引入 RAG 的根本动机。

## 二、整体架构（一张图记牢）

```
                     ┌────────────────────────────────────────────┐
  老人提问            │  RagService（门面，编排三步）                │
 "阿司匹林和降压药    │                                            │
  能一起吃吗？"       │  ① 检索 Retrieval                          │
      │              │     question → EmbeddingService 向量化      │
      ▼              │     → VectorStore 向量 Top-K（在线）         │
  /api/rag/ask       │     →（无结果降级）KeywordIndex 关键词 Top-K │
      │              │  ② 增强 Augmented                          │
      │              │     把命中切片按 [1][2] 编号拼进 prompt      │
      │              │  ③ 生成 Generation                         │
      │              │     DeepSeek 仅按资料作答 + 引用 + 免责      │
      ▼              └───────────────┬────────────────────────────┘
  回答 + sources[]                    ▼
 （answer + 引用来源）        DeepSeekService.chat()
```

三块基础设施（都是 `service/rag/` 下独立类）：

| 组件 | 职责 | 面试一句话 |
|---|---|---|
| `RagEmbeddingService` | 文本 → 向量 | 双策略：SiliconFlow bge-m3 真实向量；无 Key 降级内置哈希向量 |
| `VectorStore` | 在线向量检索 | 内存索引 + 归一化点积 = 余弦相似度，取 Top-K |
| `KeywordIndex` | 离线关键词检索 | 中文 bigram 倒排索引，向量检索不可用时兜底 |
| `RagIngestService` | 知识入库 | 药品动态抽取 + 指南/FAQ Markdown 资源文件 → 向量化 → 落库 → 重建索引 |
| `RagStartupInitializer` | 启动自愈 | 表空自动入库；表非空从库恢复内存索引 |

## 三、核心链路逐段讲（面试这么讲）

### 1. 入库链路（RagIngestService.ingestAll）

```
药品(drug_base表,动态) ─┐
慢病指南(knowledge/guides/*.md) ├─→ 生成 KnowledgeChunk 切片 ─→ 每条向量化 ─→ 落库(knowledge_chunk表)
用药FAQ(knowledge/faqs/*.md) ─┘        (title+content)        (embedding_json)   │
                                                                     ▼
                                         重建内存索引：VectorStore.rebuild + KeywordIndex.rebuild
```

几个要点：

- **三路知识源，内容与代码分离**：药品从 `drug_base` 表**动态**读（新增药品自动进知识库）；慢病指南和 FAQ 是 **Markdown 资源文件**（`resources/knowledge/guides|faqs/*.md`，带 YAML front-matter）。**加知识 = 加一个 .md 文件**，重启自动入库，不用改代码。
- **来源可溯源**：每条知识带 `source_ref` 字段（如"参考整理（仅供科普，具体遵医嘱）"），回答引用时标注来源，区分可信度——这是医疗场景的合规底线。
- **向量化文本 = title + content**：标题在前权重更高（如"阿司匹林"出现在标题，检索时更容易命中），这是工程上的小技巧。
- **幂等重灌**：`delete(null)` 清空再灌，保证重复执行结果一致；`ingestAll()` 用 `synchronized` 防止并发重灌。
- **向量落库持久化**：`embedding_json` 存 JSON 数组。这样重启后直接从库里恢复内存索引，不用重新调 embedding 接口（省钱、快）。
- **入库是批量、检索是即时**：和项目 OCR 链路（Redis Streams 异步）同一种"读写分离"思路。

### 2. 向量化（RagEmbeddingService）

**真实方案**：SiliconFlow 的 `BAAI/bge-m3`（中文向量模型，1024 维）。DeepSeek 官方没有向量接口，所以走 OpenAI 兼容的第三方。调用就是一次 POST：

```json
POST https://api.siliconflow.cn/v1/embeddings
{"model": "BAAI/bge-m3", "input": "阿司匹林和降压药能一起吃吗"}
→ data[0].embedding = [0.012, -0.045, ...]  // 1024 个浮点数
```

**降级方案（没配 Key 也能跑）**：内置哈希特征向量——把文本按**字符 bigram** 切分（"阿司匹林" → 阿司/司匹/匹林），每个 bigram 哈希到 512 维的桶里计数，再归一化。语义相近文本 bigram 有重叠，能粗粒度检索。

**关键动作：L2 归一化**。向量除以自己的模长后，任意两向量**点积 = 余弦相似度**，省去每次检索都算模长的开销。面试常问："归一化有什么好处？" → 检索从 `dot/(|a||b|)` 简化为 `dot`，计算量减半。

### 3. 在线检索（VectorStore）

- 数据量百~千条时，**内存全量遍历 + 点积**就是毫秒级，不需要 FAISS/Milvus 这种重型组件——保持项目 MySQL+Redis 轻量架构。
- `index` 用 `volatile` + 每次 rebuild 换新 List：读写无锁，重建时旧索引继续服务，重建完原子切换（volatile 保证可见性）。这是一个可以讲的多线程细节。
- 检索结果按分数降序取 Top-K，`ScoredChunk` 同时带回知识切片本体（后面拼 prompt 要用）。

### 4. 离线降级（KeywordIndex）

和向量检索互补：

- **倒排索引（Inverted Index）**：每个 bigram 词项 → 出现过的切片 ID 列表。查询时对问题切同样的 bigram，统计每篇切片命中了几个词项，命中越多分越高。
- 这是**搜索领域的经典数据结构**（Lucene/Elasticsearch 的核心就是倒排），面试可以主动讲。
- 触发时机：向量检索无结果（如 embedding 服务挂了、断网）→ 自动切关键词检索，回答仍可用。

### 5. 增强 + 生成（RagService）

组装 prompt 是关键，System Prompt 规则：

```
1. 只根据「参考资料」回答，资料里没有的明确说"资料中没有提到"，不要编造
2. 用大白话回答，面向老年人，多打比方
3. 引用参考资料时用 [1][2] 标注来源
4. 回答结尾必须加：以上信息仅供参考，具体用药请遵医嘱
5. 不做诊断、不推荐替代方案，紧急情况提示立即就医
```

User Prompt 结构：

```
参考资料：
[1] 阿司匹林
    商品名：拜阿司匹灵；分类：处方药；说明：...
[2] 用药FAQ：阿司匹林和降压药能一起吃吗？
    阿司匹林（抗血小板药）和大多数降压药可以同服...

老人的问题：阿司匹林和降压药能一起吃吗？
```

**为什么这样设计**：`[1][2]` 编号让模型"引用"有锚点，前端才能展示"根据 XX 说明书"；免责声明 + 不做诊断是医疗合规底线；大白话要求是针对老人场景的产品化细节。

### 6. 用户药箱个性化（AI 管家的关键差异）

`/api/rag/ask` 会从 JWT 上下文取当前用户 ID，查询其**药箱中「使用中」的药品**（`user_medicine_box` 表 status=active → 关联 `drug_base` 取药名），注入 prompt：

```
用户当前药箱正在服用的药：阿司匹林、硝苯地平。
如果问题与这些药有关，请优先结合它们回答，让老人感觉你了解他的用药情况。
```

效果：老人问"我这药能和降压药一起吃吗"——系统**知道他药箱里真的在吃什么**，回答完全个性化。这构成了完整的产品闭环：**拍药盒 → OCR 识别入药箱 → 药箱自动关联知识库 → AI 基于用户真实用药回答**。返回的 `userDrugs` 字段也可供前端展示"根据你的药箱：XXX"。

**三级降级**（面试亮点，呼应项目"AI+本地双引擎"）：

| 层级 | 触发条件 | 行为 |
|---|---|---|
| VECTOR | 正常 | 向量检索 → LLM 生成 |
| KEYWORD | 向量检索无结果 | 关键词检索 → LLM 生成 |
| LOCAL | LLM 不可用（无 Key/失败） | 直接返回最相关切片原文 + 免责声明 |

## 五、面试 Q&A（高频问题直接背）

**Q1：为什么不用 Fine-tuning 而用 RAG？**
RAG 无需训练、知识可随时更新（改知识库即生效）、回答可溯源引用、成本低。Fine-tuning 适合"改变模型说话风格/领域化"的稳定需求，但医疗知识更新频繁，RAG 更合适。工业界共识：**先 RAG，不够再 Fine-tune**。

**Q2：向量检索和关键词检索各有什么优缺点？**
向量检索理解语义（"这药和降压药一起吃行不行"能命中"相互作用"），但对精确名词（药名）可能不准；关键词检索精确命中名词，但不懂语义（"阿司匹林能不能和阿莫西林同服"如果没出现"相互作用"字眼可能漏检）。所以项目做了双路 + 降级。

**Q3：为什么向量做 L2 归一化？**
归一化后 `dot(a,b)` 直接等于余弦相似度，检索时省去模长计算；同时归一化让不同长度的文本可比。余弦相似度关注"方向"而非"长度"，对文本匹配语义合理。

**Q4：embedding 维度不匹配会怎样？**
点积要求两个向量长度一致。本项目 provider 在启动时固定（bge-m3=1024 或本地=512），全程不混用，所以不会出现维度不一致。这是"策略一旦选定就固定"的设计。

**Q5：知识库怎么更新/维护？**
设计原则是"内容与代码分离，加知识不加代码"：药品从 `drug_base` 表动态抽取（业务表增药即进知识库）；指南/FAQ 是 Markdown 资源文件（`resources/knowledge/*.md`，YAML front-matter 定义标题/来源/标签），**加知识 = 在对应目录加一个 .md 文件，重启自动向量化入库**。更新知识库不需要动模型、不需要重新部署 Java 代码。后续演进：管理接口（CRUD）→ 文档上传解析入库。当前向量存 MySQL 是演示规模（几百条）的正确选择，`VectorStore` 已接口化，规模大了可平滑迁移 Milvus/pgvector。

**Q6：知识可信度怎么保证？**
诚实面对数据源：当前 `drug_base` 的说明书字段是演示数据（非官方原文），因此每条知识带 `source_ref` 标注来源（如"参考整理（仅供科普，具体遵医嘱）"），回答引用时展示来源，供用户判断可信度。生产路径：老人拍照药盒 → OCR 识别说明书原文 → 官方原文入库（标记为高可信），或导入药监局等官方数据源。这也是项目"OCR → 知识库 → 可溯源回答"的数据闭环。

**Q7：RAG 的局限？为什么医疗还要加限制？**
RAG 的检索质量决定回答质量（垃圾进垃圾出）；且即便检索正确，模型仍可能"过度发挥"。所以本项目用 System Prompt 硬约束：只按资料答、不做诊断、必须免责声明——**医疗场景的 AI 不是"能力问题"而是"责任问题"**。

## 六、改造/扩展方向（面试加分）

- **混合检索重排（Rerank）**：向量 + 关键词结果合并后，用重排模型精排 Top-K
- **增量入库**：药品入库时经 Redis Streams 异步向量化，不用全量重灌
- **知识管理接口**：指南/FAQ 从资源文件升级为 DB 表 + CRUD API，线上热更新
- **文档上传**：上传 PDF/图片说明书 → 解析 → 切分 → 向量化（接 OCR 链路，官方原文入库）
- **会话记忆**：多轮对话把历史拼进 prompt（对应 README 里 P0 待办）
- **流式输出**：SSE 边生成边返回（对应 README 里 P0 待办）
- **评测集**：20 个典型问题 + 期望引用来源，回归测检索命中率
