# 系统性代码审查与优化建议报告

> 项目：AI 紧急助手系统（老年人用药管理）— 求职简历展示项目  
> 审查日期：2026-08-02 ｜ 审查分支：codex/publish-project（52c11417）  
> 技术栈：Spring Boot 2.7.18 + MyBatis-Plus + MySQL + Redis + React 18 (CRA)  
> 代码规模：后端 182 个 Java 文件，前端约 18,700 行 JS

---

## 0. 总体评价

**这是一份足以写进简历的完整全栈项目**：双端隔离（老人端/家属端）、JWT 鉴权、Redis 分布式锁、WebSocket 实时通知、外部 AI/OCR/TTS 集成、Docker 编排、GitHub Actions CI、生产配置与环境变量注入等，覆盖面在同级别个人项目中属于优秀。

**但当前处于"功能完整、工程未打磨"阶段**，存在几处会直接影响面试观感与上线安全的问题：前端巨型组件（App.js 8180 行）、控制器异常详情泄露、测试几乎为零。按 6 个维度审查如下。

```java
// ❌ 现状：异常泄露 + 恒 200
@GetMapping("/list")
public ResponseResult<List<MedicineBoxEntry>> list(@RequestParam String userId) {
    try {
        return ResponseResult.success(service.list(userId));
    } catch (Exception e) {
        return ResponseResult.fail("查询失败: " + e.getMessage());  // 内部细节泄露
    }
}

// ✅ 改进：交给全局异常处理器，业务只写主流程
@GetMapping("/list")
public ResponseResult<List<MedicineBoxEntry>> list(@RequestParam String userId) {
    return ResponseResult.success(service.list(userId));
}

// GlobalExceptionHandler 统一处理：
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public ResponseResult<Void> handleBusiness(BusinessException e) {
        return ResponseResult.fail(e.getMessage());  // 业务消息可展示
    }
    @ExceptionHandler(Exception.class)
    public ResponseResult<Void> handleUnknown(Exception e) {
        log.error("Unhandled exception", e);          // 完整堆栈进日志
        return ResponseResult.fail("系统繁忙，请稍后再试"); // 前端只见通用文案
    }
}
```

**预期收益**：消除安全信息泄露（SQL 片段、堆栈可能经接口暴露）；错误处理收敛到单点；代码量减少、可读性提升。

**JWT 登出改进方案**（Redis 黑名单，代码级方案）：

```java
// 登录/签发时把 token jti 写入 Redis（TTL = token 有效期）
// 登出时立即标记失效，过滤器校验时检查黑名单
@Service
public class TokenBlacklistService {
    private final StringRedisTemplate redis;

    public void logout(String jti) {
        redis.opsForValue().set("jwt:blacklist:" + jti, "1", 30, TimeUnit.MINUTES);
    }
    public boolean isBlacklisted(String jti) {
        return Boolean.TRUE.equals(redis.hasKey("jwt:blacklist:" + jti));
    }
}
// JwtAuthenticationFilter 增加：if (blacklistService.isBlacklisted(jti)) { 401 }
```

## 4. 健壮性与错误处理

### 4.1 现状盘点

| 项      | 现状                                                                   | 评价     |
| ------ | -------------------------------------------------------------------- | ------ |
| 全局异常处理 | `GlobalExceptionHandler` 存在，但被各 Controller 的 try-catch 绕过            | ⚠️ 需收敛 |
| 业务异常   | `BusinessException` + 统一 `ResponseResult` 封装                         | ✅ 良好   |
| 输入校验   | 部分接口用 DTO+@Valid，部分用 Map 裸收参，不一致                                     | ⚠️     |
| 事务管理   | 多处写操作无 `@Transactional`；`ScheduledTask` 事务内 try-catch 吞异常导致**事务不回滚** | ⚠️     |
| 日志     | 生产有落盘配置；但 DEBUG 级别在 dev 全开；异常日志与业务日志混杂                               | ⚠️     |
| 并发     | Redis 分布式锁实现正确（setIfAbsent+UUID），但锁无续期看门狗，5 分钟超时后可能重复执行              | ⚠️     |
| 消息推送   | Outbox 每 3 秒轮询、无重试上限/死信处理，发送+标记非原子可能重复推送                             | ⚠️     |

### 4.2 关键改进

```java
// ❌ 事务被吞：异常在事务内被 catch，@Transactional 失效（部分成功不可回滚）
@Transactional
public void generateDailyPlan() {
    try {
        doStep1();
        doStep2();  // 失败
    } catch (Exception e) {
        log.error(...);  // 事务已标记 rollback-only 或不回滚，数据半完成
    }
}

// ✅ 让异常穿透事务边界，由外层统一处理；单条失败走失败队列单独重试
@Transactional
public void generateDailyPlan() {
    List<Long> failed = new ArrayList<>();
    for (User u : users) {
        try {
            generateForUser(u);
        } catch (Exception e) {
            failed.add(u.getId());   // 记录失败用户，不中断整体
        }
    }
    failureQueue.save(failed);       // 落库后续重试，而非静默吞掉
}
```
