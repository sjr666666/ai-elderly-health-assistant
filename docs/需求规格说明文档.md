## 1. 引言

### 1.1 编写目的

本《需求规格说明书》旨在系统、完整地阐述"AI药管家"项目的功能与非功能需求，作为项目设计、开发、测试、验收以及比赛评审的基准文档。文档面向以下读者：

- **比赛评委**：理解项目目标、功能边界与技术亮点
- **开发人员**：作为编码实现与单元测试的依据
- **测试人员**：作为编写测试用例与验收测试的依据
- **产品/设计人员**：作为后续迭代规划与原型设计的参考

### 1.2 项目背景

中国正快速步入老龄化社会。根据国家统计局数据，截至 2025 年底，60 岁及以上人口已超过 3 亿。老年人群体普遍存在以下用药痛点：

1. **多重用药**：约 65% 的老年人同时服用 5 种以上药物，极易发生药品冲突与漏服
2. **用药依从性差**：记忆力衰退导致漏服、错服、重复服药现象频发，直接影响慢病控制效果
3. **药品管理混乱**：家庭药箱药品过期、临期未及时清理，存在服用过期药的健康风险
4. **信息获取困难**：药品说明书字号小、术语专业，老年人难以理解用法用量与禁忌
5. **家属远程监护缺失**：子女工作繁忙，无法实时掌握老人用药情况，紧急情况下信息滞后

传统用药管理依赖纸笔记录或简单的闹钟提醒，无法解决冲突检测、个性化指导、家属联动等深层次需求。本系统通过融合 AI 大模型、OCR 图像识别、语音合成与渐进式提醒等先进技术，构建一站式智能用药管理平台，从根本上提升老年人用药安全性与依从性。

### 1.3 项目目标

**总目标**：构建一套面向老年人及其家属的双端智能用药管理系统，实现"识药—管药—提醒—监护—咨询"全流程数字化闭环，提升老年人用药安全与依从性，缓解家属远程监护压力。

**分项目标**：

| 编号 | 目标项      | 量化指标                               |
| -- | -------- | ---------------------------------- |
| G1 | 用药依从性提升  | 通过四阶段渐进式提醒，将按时服药率提升至 85% 以上        |
| G2 | 药品冲突风险预警 | 覆盖 13 类冲突场景，新药入箱自动检测响应时间 < 1 秒     |
| G3 | 老年友好交互体验 | 18px 基准字号、语音播报、视觉降级容错，70 岁以上老人独立可用 |
| G4 | 家属远程监护闭环 | 漏服超时 10 分钟自动通知家属，紧急事件秒级触达          |
| G5 | 系统健壮性    | AI 服务异常时本地规则降级，核心功能可用性 ≥ 99%       |

## 2. 项目概述

### 2.1 系统定位

AI药管家是一款面向 C 端老人与家属的双端 SaaS 化智能用药管理平台。系统以"用药安全"为核心目标，以"AI 智能化"为差异化优势，以"双端联动"为体验亮点，覆盖老年人日常用药全流程。

### 2.2 系统架构

系统采用前后端分离的 B/S 架构，分为表现层、业务逻辑层、数据访问层、外部服务层四层。

### 3.3 监护关系模型

```
┌──────────────┐       1:N       ┌──────────────┐
│   家属用户    │ ◄─────────────► │   老人用户    │
│  (role=family)│  guardian_elder │  (role=elder) │
└──────────────┘     _relation    └──────────────┘
       │                              │
       │ 1                            │ 1
       │                              │
       ▼ N                            ▼ N
┌──────────────┐              ┌──────────────┐
│ 短信通知日志  │              │ 老人端通知    │
│ sms_notif_log │              │ elder_notif  │
└──────────────┘              └──────────────┘
```

- **绑定规则**：家属通过老人用户名发起绑定，写入 `guardian_elder_relation` 表（唯一约束 `uk_guardian_elder`）
- **解绑规则**：解绑将 `status` 置为 `inactive`，重新绑定时自动恢复 `active`，保留历史绑定关系
- **绑定通知**：绑定成功后通过 `elderNotificationService` 向老人端推送 `bind_request` 通知（含家属姓名/电话/关系），老人可在通知中"一键添加为紧急联系人"
- **权限校验**：家属访问老人详情类接口前必须通过 `hasPermission(guardianId, elderId)` 校验

### 4.2 详细功能需求

#### FR-02 药品识别（OCR）

**FR-02-01 单张图片识别**

| 项目  | 内容                                                                                                                                                                                          |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 优先级 | P0                                                                                                                                                                                          |
| 输入  | 药品包装图片（JPG/PNG/BMP/WEBP，≤10MB，尺寸 15×15 \~ 4096×4096）                                                                                                                                        |
| 处理  | 1. 文件校验（类型/大小）2. WebP 自动转 JPEG3. 保存到本地 `./uploads`4. 创建 `ocr_record`（status=pending）5. 异步调用百度 OCR `accurate_basic`6. 调用 `DrugRecognitionService.processRecognition` 走药品匹配7. 返回 taskId 供前端轮询 |
| 输出  | OcrUploadResponse（含 taskId）                                                                                                                                                                 |
| 异常  | 文件超大、格式不支持、OCR 调用失败、图片尺寸超限                                                                                                                                                                  |

**FR-02-02 药品匹配算法**

| 项目   | 内容                                                                                                                                                                                                                                                                                                                                                    |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 处理步骤 | 1. **本地提取药品名称**：`nameNormalizer.extractDrugName(rawText)`2. **AI 兜底**：本地提取失败时调用 `deepSeekService.extractDrugNameWithAI`（temperature=0.1）3. **名称标准化**：`nameNormalizer.normalize(extractedName)`4. **有效性校验**：至少 2 个中文字符或 4 个英文字符5. **数据库匹配**：`genericName`/`tradeName`/`commonName` 三字段 LIKE 查询6. **相似度计算**：通用名权重 0.5 + 商品名权重 0.3 + 俗名权重 0.2，全字段匹配 +0.1 |
| 阈值   | `MATCH_THRESHOLD = 0.6` 匹配成功；`AUTO_IMPORT_THRESHOLD = 0.3` 自动入库                                                                                                                                                                                                                                                                                       |
| 自动入库 | 未匹配但置信度高于 0.3 时：提取规格 → AI 分类处方药/非处方药 → 写入 `drug_base`                                                                                                                                                                                                                                                                                                 |

#### FR-06 渐进式提醒

**FR-06-01 四阶段渐进式提醒**

| 阶段   | 阶段标识            | 触发条件             | 提醒内容      | 通知渠道                            |
| ---- | --------------- | ---------------- | --------- | ------------------------------- |
| 阶段 1 | `pre_remind`    | 计划时段前 15 分钟（可配置） | "即将到服药时间" | 老人端通知 + TTS 温和播报                |
| 阶段 2 | `due_now`       | 到达计划时段           | "该服药了"    | 老人端通知 + TTS 正常播报                |
| 阶段 3 | `overdue`       | 超过计划时段 1 分钟      | "服药超时提醒"  | 老人端通知 + TTS 紧急播报                |

**核心机制**：

- **定时任务**：`progressiveReminderCheck()` 每分钟扫描，调用 `progressiveReminderService.processProgressiveReminders()`

- **UI 视觉差异**：四阶段使用蓝 → 橙 → 红 → 深红渐变色递进，紧迫感逐级递增
- **最高阶段选取**：弹窗根据所有提醒中最高的阶段作为头部样式，每个药品卡片单独显示自己的阶段样式

## 6. 系统边界与约束条件

### 6.1 系统边界

**系统内**：

- 用户注册/登录/档案管理
- 药品识别、药箱管理、用药计划、冲突检测
- AI 紧急咨询、用药指导、用药周报
- 渐进式提醒、漏服监控、家属通知
- 家属端仪表盘、老人详情、紧急事件处理
- 今日一课慢病科普

**系统外**（不实现）：

- 电子病历对接（HIS 系统）
- 处方流转与在线购药
- 远程医疗视频问诊
- 智能穿戴设备数据采集
- 真实短信发送（当前为模拟）
- 真实药品配送物流

### 6.2 约束条件

| 类别    | 约束                                                          |
| ----- | ----------------------------------------------------------- |
| 技术约束  | 后端必须使用 Spring Boot 2.7.x；前端必须使用 React 18；数据库必须使用 MySQL 8.0  |
| 合规约束  | 不存储真实身份证号；不提供诊断建议（仅提供药品信息）；AI 输出明确标识"非医疗建议"                 |
| 第三方依赖 | DeepSeek API（需 API Key）；百度 OCR/TTS（需 AppID/Key）；阿里云 OSS（可选） |
| 资源约束  | 单图上传 ≤ 10MB；图片尺寸 15×15 \~ 4096×4096；AI 调用超时 120s            |
| 部署约束  | 后端 8080 端口；前端 3000 端口；MySQL 默认 3306                         |
| 字符集约束 | 全库 utf8mb4 + utf8mb4\_unicode\_ci，支持 emoji 与特殊字符            |

### 6.3 假设与依赖

**假设**：

- 老人用户具备基础智能手机/电脑操作能力
- 家属用户与老人之间存在真实监护关系
- 用户提供的健康档案信息真实有效
- 药品包装图片清晰可识别

**依赖**：

- DeepSeek API 服务可用性
- 百度 OCR/TTS API 服务可用性
- 阿里云 OSS 服务可用性（可选）
- MySQL 数据库可用性
- 网络连通性
