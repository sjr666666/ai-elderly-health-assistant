# 第一部分 需求规格

## 第一章 引言

### 1.1 编写目的

本《需求规格说明书》旨在系统、完整地阐述"AI药管家"项目的功能与非功能需求，作为项目设计、开发、测试、验收以及比赛评审的基准文档。文档面向以下读者：

- **比赛评委**：理解项目目标、功能边界与技术亮点
- **开发人员**：作为编码实现与单元测试的依据
- **测试人员**：作为编写测试用例与验收测试的依据
- **产品/设计人员**：作为后续迭代规划与原型设计的参考

### 1.2 项目背景

中国正快速步入老龄化社会。根据国家统计局数据，截至 2025 年底，60 岁及以上人口已超过 3 亿。老年人群体普遍存在以下用药痛点：

1. **多重用药**：约 65% 的老年人同时服用 5 种以上药物，极易发生药品冲突与漏服
2. **用药依从性差**：记忆力衰退导致漏服、错服、重复服药现象频发，直接影响慢病控制效果
3. **药品管理混乱**：家庭药箱药品过期、临期未及时清理，存在服用过期药的健康风险
4. **信息获取困难**：药品说明书字号小、术语专业，老年人难以理解用法用量与禁忌
5. **家属远程监护缺失**：子女工作繁忙，无法实时掌握老人用药情况，紧急情况下信息滞后

传统用药管理依赖纸笔记录或简单的闹钟提醒，无法解决冲突检测、个性化指导、家属联动等深层次需求。本系统通过融合 AI 大模型、OCR 图像识别、语音合成与渐进式提醒等先进技术，构建一站式智能用药管理平台，从根本上提升老年人用药安全性与依从性。

### 1.3 项目目标

**总目标**：构建一套面向老年人及其家属的双端智能用药管理系统，实现"识药—管药—提醒—监护—咨询"全流程数字化闭环，提升老年人用药安全与依从性，缓解家属远程监护压力。

**分项目标**：

| 编号 | 目标项      | 量化指标                               |
| -- | -------- | ---------------------------------- |
| G1 | 用药依从性提升  | 通过四阶段渐进式提醒，将按时服药率提升至 85% 以上        |
| G2 | 药品冲突风险预警 | 覆盖 13 类冲突场景，新药入箱自动检测响应时间 < 1 秒     |
| G3 | 老年友好交互体验 | 18px 基准字号、语音播报、视觉降级容错，70 岁以上老人独立可用 |
| G4 | 家属远程监护闭环 | 漏服超时 10 分钟自动通知家属，紧急事件秒级触达          |
| G5 | 系统健壮性    | AI 服务异常时本地规则降级，核心功能可用性 ≥ 99%       |

## 第二章 项目概述

### 2.1 系统定位

AI药管家是一款面向 C 端老人与家属的双端 SaaS 化智能用药管理平台。系统以"用药安全"为核心目标，以"AI 智能化"为差异化优势，以"双端联动"为体验亮点，覆盖老年人日常用药全流程。

### 2.2 系统架构

系统采用前后端分离的 B/S 架构，分为表现层、业务逻辑层、数据访问层、外部服务层四层。

### 3.3 监护关系模型

```
┌──────────────┐       1:N       ┌──────────────┐
│   家属用户    │ ◄─────────────► │   老人用户    │
│  (role=family)│  guardian_elder │  (role=elder) │
└──────────────┘     _relation    └──────────────┘
       │                              │
       │ 1                            │ 1
       │                              │
       ▼ N                            ▼ N
┌──────────────┐              ┌──────────────┐
│ 短信通知日志  │              │ 老人端通知    │
│ sms_notif_log │              │ elder_notif  │
└──────────────┘              └──────────────┘
```

- **绑定规则**：家属通过老人用户名发起绑定，写入 `guardian_elder_relation` 表（唯一约束 `uk_guardian_elder`）
- **解绑规则**：解绑将 `status` 置为 `inactive`，重新绑定时自动恢复 `active`，保留历史绑定关系
- **绑定通知**：绑定成功后通过 `elderNotificationService` 向老人端推送 `bind_request` 通知（含家属姓名/电话/关系），老人可在通知中"一键添加为紧急联系人"
- **权限校验**：家属访问老人详情类接口前必须通过 `hasPermission(guardianId, elderId)` 校验

# 第二部分 数据库设计

## 第九章 数据库概述

### 9.1 数据库选型

| 项目 | 选型 | 理由 |
| --- | --- | --- |
| 数据库管理系统 | MySQL 8.0 | 开源成熟、社区活跃、性能稳定，支持 JSON 字段（用于 extra_data 等半结构化数据） |
| 存储引擎 | InnoDB | 支持事务、外键约束、行级锁，符合本项目高一致性需求 |
| 字符集 | utf8mb4 | 支持 4 字节 UTF-8 编码，可存储 emoji 与所有汉字 |
| 排序规则 | utf8mb4_unicode_ci | 基于 Unicode 排序规则，国际化友好，大小写不敏感 |
| 主键策略 | BIGINT AUTO_INCREMENT | 自增主键保证写入性能；对外暴露使用雪花算法 userId（全局唯一，避免主键暴露） |

## 第十三章 索引设计

### 13.1 索引设计原则

1. **主键索引**：所有表均使用 BIGINT AUTO_INCREMENT 主键，InnoDB 聚簇索引
2. **唯一索引**：业务唯一字段（如 user_id、username、approval_number）建唯一索引，保证数据一致性
3. **外键索引**：所有外键字段建索引，提升 JOIN 性能
4. **查询索引**：高频查询条件建组合索引，遵循最左前缀原则
5. **排序索引**：ORDER BY 字段建索引，避免 filesort
6. **避免过度索引**：写多读少表（如日志表）只建必要索引

### 13.3 索引优化说明

#### 13.3.1 组合索引最左前缀

- `idx_user_status (user_id, status)`：支持 `WHERE user_id=?` 和 `WHERE user_id=? AND status=?`，不支持仅 `WHERE status=?`
- `idx_plan_user_date (user_id, plan_date)`：支持按用户查询日历，最高频查询场景
- `idx_ocr_user_time (user_id, created_at)`：支持用户识别历史按时间排序

#### 13.3.2 覆盖索引

家属端仪表盘查询关联老人统计时，通过 `idx_guardian_id` 索引即可获取所有关联老人 ID，无需回表（覆盖索引优化）。

#### 13.3.3 避免索引失效

- 避免在索引字段上使用函数：`WHERE DATE(created_at) = '2026-06-26'` 应改为 `WHERE created_at >= '2026-06-26' AND created_at < '2026-06-27'`
- 避免类型转换：`WHERE user_id = '10001'` 应改为 `WHERE user_id = 10001`
- 避免前导通配符：`WHERE generic_name LIKE '%阿司匹林%'` 走全表扫描，应优先使用 `WHERE generic_name LIKE '阿司匹林%'`

## 第十五章 数据库性能优化策略

### 15.1 表结构优化

#### 15.1.1 字段类型优化

| 优化点 | 实现方式 |
| --- | --- |
| 主键选型 | BIGINT AUTO_INCREMENT，避免 UUID 索引碎片 |
| 状态字段 | VARCHAR(20) 而非 INT，可读性高，调试方便 |
| 布尔字段 | TINYINT(1) 而非 BOOLEAN，节省空间 |
| 金额/比率 | DECIMAL 而非 FLOAT，避免精度丢失（如 compliance_rate DECIMAL(5,2)） |
| 时间字段 | DATETIME 而非 TIMESTAMP，避免 2038 问题 |
| 长文本 | TEXT/LONGTEXT 单独存储，不放在主查询字段中 |
| JSON 字段 | extra_data 使用 MySQL 8.0 JSON 类型，支持 JSON 查询函数 |

#### 15.1.2 冗余字段优化

`medication_weekly_report` 表设计冗余字段（total_plans/taken_count/missed_count/skipped_count/compliance_rate/drug_variety_count）：

- **目的**：避免每次查询都反序列化 `statistics_json`
- **场景**：仪表盘统计、列表展示、排序查询（`idx_compliance_rate`）
- **更新策略**：生成周报时一次性写入，后续不修改

#### 15.1.3 逻辑删除优化

- 所有业务表设计 `deleted` 字段，MyBatis Plus 自动过滤 `deleted=0`
- 优势：保留历史审计痕迹，可恢复误删数据
- 劣势：占用存储空间，需定期归档（生产环境通过定时任务将 90 天前的已删除数据归档到历史表）

### 16.3 字段平滑升级

通过存储过程支持老库兼容升级（MySQL 8.0.x 不支持 `ADD COLUMN IF NOT EXISTS`）：

```sql
DROP PROCEDURE IF EXISTS add_col_if_missing;
DELIMITER $$
CREATE PROCEDURE add_col_if_missing(
    IN p_table VARCHAR(64),
    IN p_column VARCHAR(64),
    IN p_definition TEXT
)
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM information_schema.COLUMNS
        WHERE TABLE_SCHEMA = DATABASE()
          AND TABLE_NAME = p_table
          AND COLUMN_NAME = p_column
    ) THEN
        SET @sql = CONCAT('ALTER TABLE `', p_table, '` ADD COLUMN `', p_column, '` ', p_definition);
        PREPARE stmt FROM @sql;
        EXECUTE stmt;
        DEALLOCATE PREPARE stmt;
    END IF;
END$$
DELIMITER ;

CALL add_col_if_missing('sys_user', 'phone', "varchar(20) NULL COMMENT '手机号' AFTER `real_name`");
```

### 18.4 间距规范

| 类别 | 数值 | 用途 |
| --- | --- | --- |
| 容器内边距 | 40-60px | app-container padding |
| 卡片内边距 | 24-48px | 主要卡片 padding |
| 元素 gap | 8/12/16/24px | flex/grid gap |
| 模态框 padding | 40-50px | 弹窗内边距 |
| 响应式收缩 | 30/40px（1200px）、20/24px（768px） | 中小屏适配 |

### 18.5 阴影规范

```css
--shadow-soft: 0 8px 32px rgba(0, 0, 0, 0.08);     /* 默认卡片 */
--shadow-medium: 0 12px 48px rgba(0, 0, 0, 0.12);   /* 悬浮卡片 */

--shadow-glow-blue: 0 0 40px rgba(74, 144, 226, 0.3);   /* 蓝色发光 */
--shadow-glow-mint: 0 0 40px rgba(152, 212, 187, 0.3);  /* 薄荷发光 */
```

老人端阴影较重，强化层次感与悬浮感，方便老人识别可点击元素。

### 18.6 动效规范

```css
--transition-fast: 0.2s cubic-bezier(0.4, 0, 0.2, 1);
--transition-medium: 0.3s cubic-bezier(0.4, 0, 0.2, 1);
--transition-slow: 0.5s cubic-bezier(0.4, 0, 0.2, 1);
```

特殊动效：
- **header shimmer**：顶栏渐变流光动画
- **loading spinner**：旋转加载动画
- **toast-enter/exit**：Toast 进入退出动画
- **fadeInUp**：模态框淡入上滑
- **pulse**：脉冲动画（紧急按钮）
- **粒子庆祝**：服药确认后触发粒子飞散动画

### 18.7 图标规范

- **统一使用 SVG 图标**，不使用 emoji（用户偏好）
- 老人端图标较大（24-32px）
- 家属端 SVG 图标主色为 `#3A7BC8`（蓝色）
- 老人端 SVG 图标支持多彩（蓝/绿/橙/红）
- 性别头像：男 `#5B9BD5`、女 `#E88BA8`

### 23.3 视觉设计原则

1. **老人端"暖 + 大 + 厚"**：
   - 暖色渐变背景（杏色 + 薄荷绿）
   - 18px 大字号、line-height 1.8
   - 36px 大圆角、重阴影
   - 蓝色发光效果突出可点击元素

2. **状态色统一**：
   - 红 = 危险/紧急/漏服/过期
   - 橙 = 警告/临期/待处理
   - 绿 = 成功/已服/已处理
   - 蓝 = 主色/待服/链接

3. **渐进式提醒视觉差异**：
   - 蓝 → 橙 → 红 → 深红 颜色递进
   - 🔔 → ⏰ → ⚠️ → 🚨 图标语义递进
   - 紧迫感逐级递增，引导老人及时服药

> 家属端视觉设计原则（"冷 + 小 + 轻"）将在第二阶段文档中展开。

### I.4 原型设计部分：设计目标
